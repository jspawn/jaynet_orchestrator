## Actionable findings

### 1. Direct `specialist.delegate` is broken by the spawn signature

Reproduction:

```text
/specialist.delegate {"task":"Reply exactly OK without using tools.","tools":[],"verify":false}
```

Result:

```text
TypeError: slash_spawn.<locals>.spawn() got an unexpected keyword argument 'sampling'
```

`tools/specialist/delegate.py:816-820` passes `sampling` when role sampling
applies, but the slash-only spawn wrapper at `runtime/loop.py:253-259` does not
accept that keyword. `agent.spawn`, `agent.fanout`, and `architect` worked;
this is specific to the direct specialist delegation path.

**Suggested fix:** add `sampling` to `slash_spawn`'s signature and forward it as
a run override, with a direct-slash regression test.

### 2. `code.deps create` makes a venv that `code.deps list` cannot use

On a host with `uv`, `tools/code/deps.py:97-101` runs plain `uv venv`, which
does not seed pip. The list path at `tools/code/deps.py:111-115` then runs
`python -m pip list` inside that venv.

Observed result:

```text
.../.venv/bin/python: No module named pip
```

The same incomplete venv also made a subsequent `test.run` fail. A clean
agent-runtime `test.run` passed, confirming the venv as the cause.

**Suggested fix:** either create with `uv venv --seed`, or use `uv pip list`
when the venv was created by uv. Add a create → list → test.run integration
test.

### 3. `lint.run` applies shellcheck to Python files

A valid two-line Python file passed Ruff, Ruff Format, mypy, and Black. The
overall result was nevertheless `passed: false` because shellcheck also ran
and rejected the Python syntax.

`tools/lint/run.py:110-117` selects every installed linter when no explicit
list is supplied; there is no file-type applicability filter, despite the tool
description promising to run the installed linters “that apply”.

**Suggested fix:** map linters to applicable suffixes/shebangs before running.
A valid `.py` file must not fail because shellcheck is installed.

### 4. `browser.browse` does not match the installed h5i 0.5.1 CLI

The live host has **h5i 0.5.1**. Three separate results were observed:

- `action=read` → h5i reports `unrecognized subcommand 'read'`.
- `action=open, capture=true` → h5i reports `unexpected argument '--capture'`.
- `action=open, capture=false` → the wrapper gets further but reports that
  `agent-browser` is not installed.

The shipped wrapper/documentation describes the h5i 0.4.x contract. The first
two are a real version-compatibility failure, not bad test input.

**Suggested fix:** update the wrapper for the h5i 0.5.1 CLI or pin a supported
h5i version. Install `agent-browser` for the remaining runtime dependency.

  token caps were consumed by reasoning. Their transport/execution paths
