# JayNet v1.32.2 — audit fixes (slash gating, eval stub leak, cron scan)

Patch release from a combined Claude + Gemini audit pass (2026-10-14). Two
medium findings fixed, four low ones, one residual. Gemini's three "high"
findings were verified as false positives before anything was touched (they
cited functions that don't exist — `mutate_run_state`, `_run_Env_scope`,
`_check_host_public` at invented line numbers — and called the bounded
login throttle unbounded); its genuine leftovers (SSRF DNS-rebinding
TOCTOU, a subprocess-orphan sweep, big refactors) are tracked in
`ToDos_for_later.md`.

## What was fixed

- **Slash commands enforce the full tool policy** (medium). `/<tool>`
  bypassed the admin's global disable list and the per-user schedule gate
  — only the admin-only tier applied, so a globally disabled tool still
  ran when typed, and `/schedule.add` worked for accounts without the
  schedules permission. `run_slash` now takes the launcher's disabled set,
  `slash_spawn` carries it into child runs, and the voice route applies
  the schedule gate as well.
- **Eval stub tools no longer leak when a case skips** (medium). BFCL
  stubs were registered in `_setup_case_run` but unregistered only in
  `run_case`'s finally — so a `requires_tools` skip, a container-preflight
  skip, a mid-registration name collision, or any setup exception left
  them in the live registry. A leaked stub would enter the unattended
  toolset of every LATER case and chat, answering real calls with
  `{"status": "success"}` canned payloads. Setup now unregisters on every
  bail-out path.

## Smaller fixes

- **Cron scanner rewritten day-by-day.** `parse_cron` scanned
  minute-by-minute — ~2 s for impossible dates like "Feb 30", and it ran
  under the store lock in `mark_fired`, stalling the whole web server. The
  day-scan rejects those in milliseconds. Also: a stepped field without a
  range (`5/10`) now means `5-59/10`, standard cron semantics, instead of
  "minute 5 only".
- **Scheduled runs never hit the TTY confirmation prompt.** The fire path
  passes a refuse-everything confirm provider; previously a
  non-auto-confirm scheduled run on a server started from an interactive
  shell would hang forever on `input()`. Admins' `auto_confirm` bypasses
  the provider entirely, so nothing changes there.
- **Admin-planted schedules survive the owner's flag being pulled.**
  Entries created in Admin → Schedules carry `created_by: "admin"` and are
  exempt from the revocation auto-disable — "admin sets up a daily run
  for a family member" now works without also granting that account
  self-service scheduling. Self-created entries (chat `schedule.add`, or
  anything pre-upgrade) keep the old behavior.
- **`code.patch` uses `GIT_SAFE_FLAGS`** like every other git call site —
  a hostile `.git` config in a workspace can't route hooks through it.
- **Docs/description honesty:** `schedule.add` no longer promises
  auto-approval to non-admin owners (gated calls are declined at fire
  time for them); `docs/security.md` now points at the global
  `tools.schedule.auto_confirm` config — the "per-schedule auto_confirm"
  it described never existed.

## Upgrade

No config changes. Existing schedule entries without `created_by` are
treated as self-created (unchanged behavior). All gates green: full pytest
suite, ruff, mypy/complexity/ruff-hygiene baselines, rails, doc-tools,
prompt budget, catalog freshness.
