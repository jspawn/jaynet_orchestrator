Managed processes
      
    

    

      Brain, embedding, and reranker processes. Logs auto-refresh every 3 seconds when viewing.

    

    
  

  

    
GPUs

    

      The cards presets can be placed on — any count, mixed vendors/VRAM.
      id is the device index passed to HIP/CUDA_VISIBLE_DEVICES;
      label + VRAM are display hints only. A card can only be removed when no
      preset uses it.

    

    

      
      
      
    

  

  

    
server binaries

    

      Named builds a preset can launch with (llama-server, whisper-server, …). device_env is the variable used to pin
      cards: HIP_VISIBLE_DEVICES (ROCm), CUDA_VISIBLE_DEVICES
      (NVIDIA), GGML_VK_VISIBLE_DEVICES (Vulkan). A preset without a binary
      falls back to the launcher default shown below ($LLAMA_BIN env, else
      $JAYNET_HOME/bin/llama-server) — register a binary and pick it on the preset
      instead of relying on that path.

      One process = one backend: a ROCm/CUDA binary only sees its own vendor's cards.
      To split one model across mixed-vendor GPUs, build llama.cpp with Vulkan and
      point that preset at the Vulkan binary. A binary can only be removed when no
      preset uses it.

    

    

      
      
      
    

  

  


  

  

    
Preset catalog
      
      

    
    

      One row per servable model. Local entries are rendered into the generated
      proxy config automatically. Conf edits apply on the next launch.

      Device decides where the model lives: one GPU, all GPUs (layer-split — e.g. a
      big brain using all VRAM), or CPU. Two models may share one GPU if their combined
      VRAM fits. To run without a specialist, set its device to CPU or stop it in
      Models → Servers. A remote preset adopts a server that is already running —
      llama-server, vLLM or Ollama on another box, or a reverse-proxied URL.
      JayNet treats it as local (slots, boot, model.use) but never launches or stops it.

Strengths

    

      What a preset's strength tag MEANS. The brain sees this directory in its system
      prompt and delegation routes by tag (specialist.delegate strength="…");
      tag a preset in its editor above. temp overrides the serving preset's sampling
      for a child routed on the tag (agent.role_temperature; empty = preset
      default — execution cold ~0.2, ideation warm ~0.4+). Entries persist as admin config
      overrides and apply on the next run — no restart. Shipped defaults can be edited
      (marked edited) and reverted with Reset; only custom tags disappear on
      Reset.

Boot model slots
      

    

      Which preset each managed process boots by default. Takes effect on the next
      process (re)start — relaunch it in Models → Servers. Set a slot to
      (none) to run without it (e.g. no specialist, no RAG servers); an empty
      specialist falls back to the brain. specialist2/3 are optional extra
      specialists (aliases local-specialist2/3) — empty by default.

Default run budget

Backup

Connectors
      
      
      
    

    

      State (enable/read-only) lives here; editing the YAML lives in Studio → Build.
      Declarative bridges to external systems (mail, ERP, any HTTP API) — YAML, no code, so they're safe to share:
      a pack never carries your credentials or URLs (those live here, per box). Disabled removes a connector's
      tools entirely; read-only keeps only its read tools (writes vanish, not just gate). Write tools always ask
      for confirmation in chat. Changes apply immediately — no restart. Build one in the Studio, import/export as
      .jayconn. For raw MCP servers use Harness → MCP instead.

    
    

  

  


  

  

    
Plugins
      
        
        
      

    
    

      Optional capability bundles. builtin plugins ship with JayNet (off by default —
      they usually need extra pip packages); installed plugins live in the data dir's
      plugins/ folder (on by default) — drop a folder in or install a
      .jayplugin pack here. Toggling applies live — tools, skills,
      routes and UIs appear/disappear without a restart (new runs only; a restart is
      only needed for brand-new pip dependencies). A freshly installed plugin shows
      load now until first activated. An unavailable plugin lists
      the pip packages it's missing; a needs bin: note lists executables some
      features need (never blocking). A plugin with a UI gets an open button —
      it loads inline below the table.
      Plugins are admin-installed code running with full
      trust — only install code you audited.

Eval cases
      
      

    

      Behavioural test cases played through the real agent loop and graded by a judge
      model. Custom cases live in the data dir and layer over the built-in seeds — on an
      id clash the custom one wins; built-ins are read-only here (duplicate one to
      customize it). Export/import travels as .jaypack via Studio → Build.
      Tick cases to run a selection (or click a row to inspect it). Disabled
      cases are skipped by Run-all, tag and scheduled runs — deactivate the ones your
      current brain can't pass yet instead of deleting them.

Run

    

      Runs play cases through the live agent loop (unattended toolset) and grade them
      with the judge model — they cost real money, capped by the eval config. One suite
      at a time. Judge and driver models are configured in Config → eval.judge_model /
      eval.driver_model (default and fallback: local-specialist).

    

      
      
      
      
      
      
      
      
    

    

    
Run-all and tag runs skip disabled cases; an explicit selection runs even a disabled one. Run delta skips cases that passed their last 3 runs but spot-checks a random 10% of them.

    

    

  


  

    
Tool telemetry

      calls, error rate, share of runs, ok-rate with vs without. High use + high errors =
      a lane that needs work; near-zero calls over thousands of runs = trim candidates
      (check before cutting — some tools are rare by design). The ok-rate contrast is
      correlation, not causation: hard runs call more tools. Playbook §6 argues from this.

Scheduled runs

      same suite path and land in the results ledger tagged with the JayNet version,
      so a regression after a release or brain swap becomes a number. Skipped while
      any suite is running; a schedule whose case/tag disappears is disabled.

Benchmark variants

    

      A variant is one line-up of the suite: a model alias plus sampler overrides —
      three different brains, or the same brain at three temperatures. The label is
      recorded as the result's brain and is what the comparison below groups by.
      Harness: full runs the whole toolset (delegation included —
      JayNet's model routing); brain only strips specialist.delegate / architect /
      agent.spawn, so you can A/B what the routing actually buys. A case that
      requires a stripped tool skips instead of failing.
      Pin temperature: 0 + a fixed seed for repeatability
      (best-effort: batching and cloud providers still wobble, so run reps and
      compare pass rates, not single runs).

Strength matrix 

    

      Measured pass rates per brain label × strength — every result counts under
      each strength its case exercises (case tags → strengths; imported tb/gaia
      cases map to coding/research). Live runs and benchmark reps both feed it.
      This is the measured truth behind preset strengths tags; the tags
      themselves (and the benchmark priors on new HF presets) are only the
      cold-start prior. To measure a model: run a benchmark variant with its
      alias over a tag that maps to the strength (e.g. tb → coding).
      Rows are brain labels; labels without a current preset hide by default.
